# 사용자가 지정하는 공통헤더와 메시지 검증

헤더 타입명·멤버명·ID 숫자를 고정하지 않습니다. 사용자가 선택하는 것은 **ID 역할 필드의 위치·비트 폭**, **Length 역할 필드의 위치·비트 폭**, **헤더 전체 크기**, endian과 비트 순서입니다. 모든 가져온 메시지는 이 배치와 크기를 만족해야 합니다.

## 공통헤더 타입을 한 번 등록하는 이유

공통헤더와 일반 메시지의 역할을 나눕니다. 공통헤더는 여러 메시지가 함께 참조하는 타입 정의이고, 메시지 파일은 실제 기록·해석 대상입니다. 인터페이스 관리의 **공통헤더 형식 지정·관리**에서 메시지가 없는 상태로도 헤더를 먼저 저장할 수 있습니다. 이 원본은 내부 암호화 저장소에 보관하며 새 프로파일과 다음 실행에서도 재사용합니다.

예를 들어 `samples/MessageHeader.h`를 등록한 뒤 ID 역할로 `id`, Length 역할로 `length`를 선택합니다. 이후에는 `samples/TestPack.h`만 선택해도 아래 이름 참조를 해결합니다.

```cpp
struct MessageHeader {
    uint16_t id;
    uint16_t length;
};
struct TestPack {
    MessageHeader Header;
    char label[4];
    UCHAR mode : 3, status : 5;
    const unsigned short int first, second;
    signed int delta;
    unsigned long long counter;
    long timestamp;
};
```

`MessageHeader`와 `Header`, `id`, `length`는 예시 이름입니다. `UserHeader Envelope;`를 사용할 수도 있고, ID 역할을 `code`, Length 역할을 `extent`에 지정할 수도 있습니다. C++ 타입 참조 자체는 선언한 타입 이름과 같아야 하지만, ICD 검증은 실제 메시지의 필드 이름이 아니라 **선택한 위치·비트 폭·수치 비트 배치**로 판단합니다. 다른 이름의 정수 필드라도 같은 배치이면 정상입니다.

Windows LLP64 및 pack1에서 위 TestPack은29바이트/전개 필드13개이며 Header.id는 byte0의16비트, Header.length는 byte2의16비트입니다. UCHAR 등 Windows 정수 별칭, 배열, 비트 필드, 기존 typedef를 처리합니다. pack/endian/bit order를 명시하며 네이티브 컴파일러 ABI를 추정하지 않습니다.

## 화면 사용 순서와 각 동작의 의도

1. **공통헤더 형식 지정·관리**: 사용자의 헤더 파일(.h/.hpp 또는 CSV)을 선택하고 사용할 구조체/메시지, ID·Length 역할 필드를 고릅니다. C++ 타입 이름 재사용은 선언이 있는 .h/.hpp 원본을 사용합니다.
2. **헤더 전체 크기**: 구조체 크기로 초기화되며 직접 수정할 수 있습니다. 최소한 선택한 두 필드를 모두 포함해야 합니다. 지정한 전체 크기는 모든 새 메시지에 반드시 포함되어야 합니다. ID·Length 두 필드만 맞더라도 메시지가 이 크기보다 작으면 오류입니다.
3. **현재 메시지의 헤더 검증**: 메시지별 위치·비트 폭·엔디언·헤더 전체 크기의 검증 결과를 표시합니다. 실제 ID 숫자에 대한 기대값은 입력하지 않습니다.
4. **공통헤더 형식 저장**: 헤더 원본과 정의를 관리자용 내부 저장소에 즉시 암호화 저장합니다. 현재 메시지에 문제가 있어도 헤더 타입 자체를 먼저 등록할 수 있으며 현재 메시지 오류는 별도로 표시합니다.
5. 가져오기에서 **C/C++ 메시지 파일 선택** 후 **선택 파일을 메시지로 추가** 또는 **선택 파일로 ICD 교체**를 누릅니다. 등록한 공통헤더 파일을 다시 선택할 필요가 없습니다. 선택 파일에서 선언한 메시지만 가져오고 공통헤더 타입을 일반 메시지로 중복 추가하지 않습니다. CSV 가져오기도 등록한 타입 정의를 참조할 수 있습니다.
6. 메시지 전부를 검증합니다. 하나라도 배치나 헤더 전체 크기가 맞지 않으면 적용을 거절하고 기존 ICD를 유지합니다. 검사에서 실패한 메시지를 조용히 제외하지 않습니다.
7. 현재 ICD에서 메시지별 필드를 확인하고 **계정 저장소에 암호화 저장**을 누릅니다. 공통헤더 형식 저장과 프로파일 저장은 각각 명시적인 작업입니다.

이전의 참조 헤더 추가/교체/해제 버튼 대신 메시지 추가/교체 동작을 명시했습니다. 같은 타입이 다른 파일에도 동일하게 선언되면 재사용하며, 동일 타입 이름에 다른 선언이나 pack이 들어오면 충돌을 보고합니다. include나 C 코드를 실행하지 않습니다.

## 실제 패킷 처리

- 완전한 UDP 데이터그램과 송수신 IP·방향을 검사합니다. 잘린 IP/UDP, 비UDP, 조각·미지원 확장 헤더 등은 제외합니다.
- 지정한 ID·Length 위치에서 raw 비트를 읽습니다. ID 값은 미리 제한하지 않습니다.
- Length는 사용자 설정에 따라 전체 UDP payload 크기 또는 헤더 제외 크기와 일치해야 합니다.
- 실제 payload 크기는 정확한 ICD 메시지 크기와 같아야 합니다. 부족하거나 여분인 바이트를 허용하지 않습니다.
- 동일 구조·크기의 메시지가 여러 개이거나 여러 인터페이스에 동시에 맞으면 식별할 수 없으므로 모호한 패킷으로 제외합니다. 첫 메시지를 임의 선택하지 않습니다.
- 통과한 원본 프레임·타임스탬프·링크 타입을 NIC→인터페이스별 표준 PCAP에 보관합니다. PCAP→CSV도 같은 검사를 다시 수행하며 범위 검사는 해석 후 별도로 적용합니다.

현재 체크섬은 없음 모드이며 IPv4/IPv6 조각 및 TCP 스트림 재조립은 하지 않습니다. 이전 버전의 ID 매핑·본문 전용 정책은 호환성을 위해 읽지만 새 공통헤더 설정은 모든 메시지에 헤더를 포함하는 방식입니다.

## 저장과 권한

공통헤더 원본은 SharedHeader 관리자 암호화 봉투로, 프로파일 ICD·원본 헤더와 기록 규칙도 각각 암호화하여 같은 Windows 사용자별 workspace.bin에 저장합니다. 파일 전체는 Windows DPAPI 및 관리자 서명으로 보호합니다. guest에는 원본 타입 라이브러리를 제공하지 않고 기록에 필요한 최소 매칭 규칙만 별도 봉투로 전달합니다. guest의 허용 ICD만 CSV로 해석하는 권한은 유지합니다.

## 메시지 파일 자체에서 헤더 앞부분을 지정하는 경우

공통헤더 선택 목록에서 TargetTrack 같은 전체 메시지 타입을 골라 ID/Length와 헤더 크기4바이트를 지정할 수도 있습니다. 이는 선택 필드의 배치를 재사용하는 것이며 TargetTrack 전체를 메시지 목록에서 제외한다는 뜻이 아닙니다. 같은 .h 파일을 다시 선택해 메시지 추가하면 TargetTrack을 그대로 가져옵니다.

선택 파일의 최상위 구조체를 메시지로 가져오고 그 안에서 참조하는 보조 구조체는 중첩 필드로 펼칩니다. 보조 타입을 별도 메시지처럼 검사해 헤더 오류를 내지 않습니다. 서로 참조하지 않는 최상위 메시지가 여러 개 있으면 모두 검증하며, 헤더가 틀린 최상위 메시지는 계속 오류로 거절합니다. 헤더 역할로 선택한 구조체 이름만 보고 메시지를 제외하지 않습니다. samples/TargetTrack.h는 중첩 TrackEntry와 이 경로를 검증하기 위한 합성 예제입니다.
